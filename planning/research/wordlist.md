# Research: wordlist

_Auto-captured from the 2026-09-02 research workflow._

## Summary

The "wordlist" in A-Z+T is not a data structure — it is a **whole LIFT XML file** (`SILCAWL.lift`) parsed by the same `io_put/lift.py::LiftXML` class as any project database, with `tostrip=True` so only a shallow parse runs. `backend/core/templates.py::CAWL` loads it, validates the user's language tag, picks a new filename, strips every `lexical-unit`/`citation` form (leaving glosses + POS + CAWL tags as empty slots), backfills illustrations, and writes it out as the user's new project. That file is **not bundled**: `lift_templates/SILCAWL` is gitignored and is `git clone`d at runtime from `https://github.com/kent-rasmussen/lift_templates.git` into the *parent* of the azt checkout, then symlinked in (`utilities/sister_repos.py:63-68`). Internet is required the first time; after that it is local. Images are a second, ~hundreds-of-MB sister repo (`images_CAWL`) plus a GitHub-API fallback resolver. Each wordlist entry carries: multiple `sense/gloss[@lang]` (the CAWL's own gloss languages are what the demo flow offers as choices), `sense/grammatical-info@value` literally `'Noun'`/`'Verb'` (remapped to the project's POS names on import), `sense/field[@type='SILCAWL']/form/text` = a **4-digit zero-padded tag** (`0001`), and `sense/trait[@name='semantic-domain-ddp4']` (copied on merge but otherwise unused anywhere in the app). Images are NOT in the LIFT — they are resolved from the tag number + underscored English gloss, e.g. directory `0001_body/`. On the key question: the `WordListTemplate`/`CAWL` split *looks* like a clean extension point (and `planning/DEKEREKE_IO_PLAN.md:69-99` already treats it as one), but `'SILCAWL'`, `'cawl*'`, `1700`, and `'{:04}'` are hardcoded in ~20 further places outside the template class — the LIFT URL/query builder, the field-type/`getlang` dispatch, the image resolver (which *raises* for any other wordlist name), the merge routine, and above all `tasks/chooser.py::getcawlmissing` which literally iterates `range(1700)`. Word-by-word entry ("Add a Word") exists but is gated behind `cawlmissing` being empty, i.e. behind having all 1700 CAWL tags — and the branch that fires otherwise contains a live `str.format` bug (`"{}".format(count=…)` → IndexError) that is swallowed by a broad `except`, so in a non-CAWL project the big action button silently does not render at all. On dialects: LIFT + the code genuinely support multiple analangs (`db.analangs`, per-analang polygraphs/profiles, an analang picker, `-x-dialect` private-use subtags in the new-project dialog), but only **one analang is active at a time**, switching restarts the app, the picker only lists analangs already present in the data (a brand-new dialect tag can only be forced by hand-editing the project JSON), and — critically — the alphabet and sort-status stores are **not keyed by analang**, so two dialects in one project would collide. Kent's actual practice, visible in `io_put/lift.py`'s `__main__`, is one LIFT file per dialect (`lol-x-his30240`, …), compared across files by CAWL number via the script-only `analyze_relationships()`.
