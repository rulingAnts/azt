# Completeness critic

## Recommendation

Before any more design work, close five cheap gaps in this order. (1) Read rulingAnts/QWOM_Data yourself: QWOM already exists as a 987-row Dekereke XML with EN/ID/Tok Pisin glosses AND a CAWL cross-reference on 973 rows — which means the Dekereke importer IS the QWOM importer, and A-Z+T's existing CAWL-keyed image resolver would light up for 973 items with no new resolver. That single fact rewrites the answer to \"could it use QWOM instead of CAWL\" and should be in the plan. (2) Settle the QWOM licence provenance (the repo asserts CC BY-NC-SA 4.0 but the SIL archive record shows no rights field and the README was drafted with Gemini). NC blocks bundling into GPL-3.0 A-Z+T but not the sister-repo runtime-clone pattern A-Z+T already uses for SILCAWL — so ask Steve Miller/Brendon Yoder for a written statement and design for runtime download, not vendoring. (3) Source the claim \"Kent suggested XSLT\" — it appears nowhere in the issue tracker (0 hits across both repos) and it is the only thing making Phase 1 use lxml+XSLT against two investigations and against the fact that A-Z+T's own XSLT chain is developer-gated and commented \"This isn't working yet\" (io_put/xlp.py:75). If it came from email, quote it in DEKEREKE_DECISIONS; if it is a paraphrase, drop it and use stdlib ElementTree. (4) Run A-Z+T once on a real Fayu LIFT before writing any code or bug report: the cawln AttributeError (io_put/lift.py:678), the missing beta/phi segments, and the format-string bug are all one 20-minute session away from being confirmed on real data — and three tiny, obviously-correct upstream fixes are a far better first contact with a maintainer who has never merged an outside PR than a whole new I/O subsystem. (5) Re-scope Phase 2 around a verified constraint, not a hoped-for one: `instance.type` is CHECK-constrained to ('editor','recorder','') in production D1 and the claim path rejects a type mismatch, and the append-only command array is returned whole on every poll — so per-row assignment for 987 words is not expressible today. Phase 2's first deliverable should be a schema+transport change (typed payload, batched/range assignment, scope expressed in settings rather than one command per row), and Quickstart_Android and tone_comparison_app should be evaluated as the actual starting code before anything is designed from scratch.

## Contradictions
- SILCAWL content: the qwom investigation downloaded https://raw.githubusercontent.com/kent-rasmussen/lift_templates/master/SILCAWL.lift and parsed it (1,700 entries; 1,696 filled Indonesian glosses; MIT licence), while the wordlist and userguide investigations — and verification 1, which re-affirmed it — all state the content "could not be verified because the file is not on this machine" and that settling it requires cloning the repo. It is settled: fetch the raw URL. Verification 1 repeated a stale uncertainty.
- QWOM size: the qwom investigation's planning number is ">1,900 items" (Miller 2024, DIAL proceedings). The actual machine-readable QWOM in Seth's own repo has 987 <data_form> records. Both statements can be true (the paper counts open-ended prompts and expected yield), but every effort estimate must use 987 template rows, not 1,900 — and the discrepancy needs one sentence of explanation from Miller/Moe.
- QWOM licensing: the qwom investigation concluded there is "no CC licence or rights statement" on the SIL record and that SIL's default terms forbid mirroring "in part or whole" without written permission. rulingAnts/QWOM_Data is a public mirror asserting CC BY-NC-SA 4.0. Unreconciled, and it is the gating fact for shipping QWOM with A-Z+T.
- XSLT/lxml: planning/DEKEREKE_DECISIONS.md #4 ("Kent suggested XSLT"; A-Z+T "already depends on lxml ... mirrors an existing in-repo pattern") directly contradicts the minimal-dekereke investigation and verification 2 ("lxml/XSLT is exactly the dependency style this codebase avoids" — lift.py:8-15 disables lxml, test_import_smoke.py:53 makes it optional, xlp.py imports it lazily and returns on ImportError). Both sides cite io_put/xlp.py; the real disagreement is whether that XSLT chain is a pattern or a dead path (Report.close() calls compile() only when me=True, marked "This isn't working yet", xlp.py:58-76). Nobody reconciled it and it decides Phase 1's implementation.
- Multi-speaker/dialect support: DEKEREKE_DECISIONS #18 says A-Z+T has "no concept of multiple speakers or dialects (one incidental hit, at backend/langtags.py:461)", while the wordlist investigation shows dialects ARE first-class (db.analangs, -x-dialect private-use subtags at ui_shell.py:2936-2951, per-analang polygraphs/profiles) and the data layer tracks a LIST of audiolangs with per-field recorded counts (io_put/lift.py:1612-1625). The accurate statement is narrower and more useful: modelled but single-active, with alphabet/status stores not keyed by analang (settings/__init__.py:240-253) and exactly one audiolang silently chosen (see newFindings).
- Minimal-diff size: the minimal-dekereke investigation claims "exactly one changed line outside the new module" and, in the same report, lists 4 hunks including a ~10-line new method; verification 2 caught this. Additionally templates.CAWL is instantiated at two sites (ui_shell.py:3170 and :3285).
- Localisation inventory: the capabilities report lists "Lingala (DRC)" among five shipped catalogs without noting the africa report's finding that ln_CD is 1,549/1,549 untranslated (a 464-byte header-only .mo). The honest count of usable non-English UIs is three (fr, es, ar), plus a half-done zh.

## Weak but load-bearing claims
- "Kent suggested XSLT" (planning/DEKEREKE_DECISIONS.md #4). This one sentence determines Phase 1's entire implementation approach and overrides two investigations, yet it is unsourced and absent from GitHub. Settle it by quoting the actual message, or drop it.
- "A-Z+T already depends on lxml ... so an XSLT-driven transform adds no dependency and mirrors an existing in-repo pattern" (DEKEREKE_DECISIONS #4). requirements.txt:21 does list lxml, but io_put/lift.py:8-15 has the import commented out with `lxml=False`, tests/test_import_smoke.py:53 treats it as optional (absence = skip, not failure), and the io_put/xlp.py XSLT chain it points to is only invoked when me=True and is annotated "This isn't working yet." (xlp.py:75). Copying a pattern the maintainer never got working is a weak precedent to build a PR on.
- QWOM's CC BY-NC-SA 4.0 status. Load-bearing for whether A-Z+T may offer QWOM at all, and asserted only in Seth's own repo README (drafted with an LLM) against a SIL archive record with no rights field. Separately: NC forbids bundling into GPL-3.0 (GPL permits no added restrictions), while the sister-repo runtime-clone pattern (utilities/sister_repos.py:63-68) avoids bundling — but that path has never been exercised for a non-SILCAWL word list, and io_put/lift.py:139-145 raises ValueError for any other word_list_field_name.
- QWOM "more than 1,900 items" as a planning figure. The artefact that exists has 987 rows. Collection-effort and 1700-vs-N gate estimates built on 1,900 are wrong by ~2x.
- "Dekereke does native LIFT import/export as of the 2026-08-22 build." Sourced from Casali's page only; nobody installed the Mac build or inspected the LIFT it emits. If that path is already good, the user-visible value of Phase 1 shrinks to tone and column fidelity — and DEKEREKE_DECISIONS #5 ("target the LIFT A-Z+T emits") assumes a gap nobody measured.
- Verification 1's "A-Z+T on current main cannot open a Papua database at all." The mechanism is real and I confirmed the code path, but the reproduction used a synthetic two-entry LIFT; it has not been shown on a real FLEx export, and the corollary (that the same path would fire for any un-illustrated sense in a CAWL project) has not been checked. Test both before this becomes the headline of a bug report.
- "Offline after first fetch" (capabilities). First run pip-installs a multi-GB dependency set and clones sister repos, and verification 1 found a database load can trigger a several-hundred-MB images_CAWL clone from a CWD-relative path (io_put/lift.py:3163-3165). For Jayapura bandwidth this is the practical gate on whether A-Z+T is usable at all, and it has never been run end to end.
- ADRs 0001 and 0003 are both "proposed" and AI-drafted, and 0001 says explicitly it is "not yet reviewed/owned by the maintainer" (verification 2). The collab investigation cites them as standing contracts; citing them that way in an upstream PR would misfire.
- "No human outside contributor has ever landed a PR" as the risk framing. True, but the better predictor is that Kent replied substantively to both of Seth's issues (#164, #165) within days. The evidenced risk is not hostility to contributions; it is his stated unwillingness to maintain format transforms — which argues for an optional-import, self-contained, well-tested module and a pre-PR question, not for abandoning the attempt.
- The medium-confidence wordlist alternatives (Holle lists, the 239-item UNCEN-SIL Papua survey list, MLE4000) are moot for the phonology use case now that a 987-item Indonesian-glossed QWOM in Dekereke XML is in hand; keep MLE4000 (CC BY-SA, 5,328 entries, verified LIFT) only as the dictionary-stage option under ROADMAP Phase 2's LIFT case.

QWOM also already ships the Indonesian glosses A-Z+T's Indonesian-speaking colleagues need (979/987), independent of any UI translation.

- FlexText hard constraint on Phase 2: worker/schema-current.sql:89 declares `type TEXT NOT NULL CHECK (type IN ('editor','recorder',''))`, and docs/js/sync.js:303-305 refuses a claim with `type_mismatch` when `iface.appType()` differs from the invite's type (app.js:7816 supplies only 'recorder'|'editor'). Adding a wordlist or tone app type therefore requires a production D1 migration of the instance table — the schema header at line 10 notes a previous instance-table rebuild — not merely a written API. "Make pairing data-type agnostic" starts as a schema change.
- FlexText assignment does not scale to wordlist rows. The device poll returns the ENTIRE commands array (worker/src/v1.js:3606 returns `commands: blob.commands || []`), seq is derived from the array tail (2907-2908), pruning acked commands is explicitly forbidden, and no cap, pagination or size guard exists anywhere in the route. One `assign` per word means 987+ permanently-retained commands in one D1 TEXT cell re-sent on every changed poll. Per-row assignment needs a different mechanism (range/batch assign, or scope expressed in the settings blob) — this is the single biggest unstated design constraint on the app Seth described.
- "Speaker identity as a device-level setting" (ROADMAP Phase 2, surface 3) has zero existing grounding: the only `speaker` in the suite is ELAN tier participants (docs/js/eaf-read.js:269-286, looksMultiSpeaker) and paragraph-export rendering. Nothing device- or instance-scoped exists to extend.
- A-Z+T's live multi-speaker behaviour, stated precisely: io_put/lift.py:1612-1625 builds per-audiolang counts of fields with sound files, so several speakers' audio survives in one LIFT — but tasks/chooser.py:360-370 picks ONE, using db.audiolang if set, else the first audiolang whose tag merely CONTAINS the analang string (`maybeals[0]`). Two speaker-tagged audiolangs (fau-x-sp1-x-audio, fau-x-sp2-x-audio) both match and one is silently chosen. Also, when nothing matches, `al` is used unbound at chooser.py:370 (NameError on the first analang). Note the frequently-quoted hard exit on multiple audiolangs (setdefaults.py:20-29, "More than one audiolang! Set this up! (exiting)") is DEAD CODE — tests/test_import_smoke.py:43 records setdefaults as a standalone script not imported by the app.
- "Kent suggested XSLT" has no trace in either issue tracker: `search/issues q=repo:kent-rasmussen/azt XSLT` and the same for rulingAnts/azt both return total_count 0, and issue #165's only two comments are Seth's QWOM_Data link and Kent's LIFT/transforms reply (verbatim as quoted in the investigations).
