# Research: flextext

_Auto-captured from the 2026-09-02 research workflow._

## Summary

The FlexText suite is ONE shared JS engine (`docs/js/`, ~35k lines, no build step) worn by five faces selected by a `window.__MODE` flag: editor, recorder, researcher panel, crowd recorder, paragraph-analysis. Each face is a 60–140 line `index.html` shell at its own origin/path (PWA scope isolation), published either from GitHub Pages (`productionWeb:/docs`) or from per-app git-connected Cloudflare Workers under `apps/<name>/` that just `cp -R docs/. public/` and serve `sw.js` with `no-store`. The only server is one Cloudflare Worker (`worker/src/v1.js`, 4151 lines) + D1 (11 tables) + R2 + Google Drive; the Worker holds the researcher's Drive OAuth refresh token and is a stateless relay — all bulk content lives in the researcher's own Drive, never in D1. The assignment machinery is a two-lane desired/reported state model: a researcher creates an `instance` (a named device slot) with a per-instance AES key Ki, mints a single-use `invite` whose secret rides the URL fragment, the device claims it with a locally minted `install_id`+secret+RSA keypair, both screens show a worker-minted 6-digit `pair_code`, the field user "accepts" and the researcher "approves", and only then does the researcher deliver Ki wrapped to the install's public key. From then on the device polls `GET /v1/instances/<id>?since=<rev>` every 20 s for an append-only, seq-numbered command array (`assign|delete|changeSettings|triggerUpload|uploadDelete|setDone`) whose payload is AES-GCM ciphertext, and POSTs an encrypted inventory to `.../report` with a monotonic `ack_seq`. Assignment scope is per-DEVICE, not per-text or per-field: `docInScope()` in app.js:3706 is a stub returning `true`, and what a coworker may see or do is controlled by a pushed settings blob (the `GROUPS` schema at researcher-panel.js:534) — writing systems, allowed toolbar buttons, delete/done permissions, consent flow, export set. Results return by the device streaming its bundle through the Worker into `FlexText Uploads/<device>/<text>/` in the researcher's Drive (single POST ≤16 MB, chunked resumable above, with Drive's own byte count as resume truth); the panel then reads the folder listing and downloads via `/v1/researcher/drive-file/<id>`. Offline is the default posture: service-worker precached shell, IndexedDB for everything, uploads queued in IDB that retry forever, assignment downloads that retry when connectivity returns, and a claim/report protocol built to be idempotent under lost responses. i18n is a single `S = { en: {...}, id: {...} }` dictionary in `docs/js/i18n.js` with `t()`, `data-i18n` attributes, and a computed `LANG_COMPLETE` gate that refuses to offer a language until its dictionary covers every English key. For a Dekereke-XML wordlist app, the worker, D1 schema, pairing/claim protocol, sync client, upload queue, recording UI, i18n and per-app Cloudflare deploy pattern are all payload-agnostic and reusable essentially as-is — the FlexText-specific parts are `flextext.js`, the `assign` command's `title/audioUrl/flextextUrl` field names, and the panel's assign modal's parse/validate step.

- **[high]** The ASSIGNMENT model's core data structure is two opaque JSON blobs on two D1 rows: `instance.desired_blob` (researcher→device: `{settings:{}, commands:[]}`) with a monotonic `desired_rev`, and `install.reported_blob` (device→researcher: encrypted inventory) with `reported_rev` and `ack_seq`.

  - _implication:_ This is the schema to copy verbatim for a wordlist app. It is payload-agnostic: the blobs are opaque to the Worker, so Dekereke rows/columns fit without any schema change.

- **[high]** Commands are an append-only array with server-derived `seq` from the array TAIL, and pruning acked commands is explicitly forbidden — the seq monotonicity is what makes cancel safe and makes the device's `seq > ack_seq` filter correct. Allowed types are a fixed allow-list of six.
  - _evidence:_ worker/src/v1.js:2885-2887 `if (!['assign','delete','changeSettings','triggerUpload','uploadDelete','setDone'].includes(cmd.type)) return 400`. v1.js:2891-2911 the CAS loop: `const seq = (blob.commands.length ? blob.commands[blob.commands.length-1].seq : 0) + 1; blob.commands.push({...cmd, seq, at: now});` then `UPDATE instance SET desired_blob=?, desired_rev=? WHERE instance_id=? AND desired_rev=?` (compare-and-swap, 5 attempts). v1.js:2896-2907 '⚠ SO: DO NOT PRUNE ACKED COMMANDS FROM THIS BLOB'. Cancel refuses `seq <= MAX(ack_seq)` (v1.js:2943-2946). Covered by test/command-seq-invariant.test.mjs.
  - _implication:_ Wordlist commands would be new members of that allow-list (e.g. `assignWordlist`, `setRowDone`). The seq/ack/CAS discipline is battle-tested and should be lifted unchanged; the comment names the exact bug that pruning reintroduces.

- **[high]** The full pairing handshake is five distinct steps with mutual verification, and it is the most directly reusable subsystem: mint invite → device claims with locally minted identity → 6-digit pair_code shown on BOTH screens → device user accepts → researcher approves + delivers Ki.
  - _evidence:_ Mint: worker/src/v1.js:2854-2873 `POST /v1/instances/<id>/invite` inserts `invite(invite_id, instance_id, sha256(secret), expires_at)`, TTL clamped 5 min…30 d (default 7 d). Link shape: docs/js/researcher.js:517-520 `${base}?invite=<id>#k=<secret>` — secret in the FRAGMENT so it never reaches a server log. Claim: v1.js:3611-3664, one atomic D1 batch gating on `claimed_at IS NULL AND expires_at>now`, plus `UPDATE install SET revoked=1 WHERE instance_id=? AND install_id<>?` (single-live-device). Pair code: `mintPairCode()` six decimal digits, worker/migrate-pair-code.sql explains why it is server-minted not fingerprint-derived (~20 bits is grindable offline). Accept: v1.js:3283-3290 (install-authed). Approve: v1.js:3265-3281 sets status='approved' and NULLs pair_code. Key delivery: v1.js:3292-3317, refuses with 409 `not_accepted` if the device hasn't accepted, and bumps `desired_rev` in the same batch so a re-key actually reaches an idle device.
  - _implication:_ Copy this wholesale. Every step exists because a specific field failure happened (the pair_code replaced a 12-second toast showing a hex fingerprint that coworkers could never reproduce — researcher-panel.js:2582-2593).

- **[high]** Client-side claim is idempotent-by-construction: the install identity (uuid + 24-byte secret + RSA-OAEP keypair) is minted and persisted to localStorage/IndexedDB BEFORE the first POST, so a dropped response loses nothing and a retry is a no-op.
  - _evidence:_ docs/js/sync.js:261-334 `claim()`: 'Mint install identity LOCALLY and persist BEFORE the first POST (plan §D.1)'. sync.js:281-283 builds the session object; :288-295 generates the keypair, stores the private key non-extractable in IndexedDB (`flextext-sync`/`keys`/`install-private-key`), sends only the SPKI public key. Worker side uses `INSERT OR IGNORE` + read-back of the stored pair_code (v1.js:3660-3663) precisely so the retry path shows the same number.
  - _implication:_ Reusable as-is. This is the piece that makes pairing work on a connection that drops mid-request, which is the normal case in Papua.

- **[high]** SCOPING IS PER-DEVICE, NOT PER-TEXT OR PER-FIELD. `docInScope()` is a stub returning true; a managed device reports and exposes its ENTIRE local corpus to its enrolled researcher.
  - _evidence:_ docs/js/app.js:3700-3708: comment 'A managed device exposes (reports + allows remote upload/management of) its FULL corpus… (Drops the earlier created>=enrolledAt data-scoping — "layer C" — per Seth 2026-06-30…)' followed by `function docInScope(/* d, enr */) { return true; }`. ## Open questions
- Does the wordlist app need per-ROW or per-FIELD scoping (speaker A sees items 1-200, speaker B 201-400)? FlexText has no such mechanism — docInScope() is a stub and scope is per-device — so this is genuinely new design, not a port.
- Does the wordlist payload need concurrent multi-device editing of the SAME list? FlexText deliberately has no merge algorithm: one instance = one live install, and a fresh claim revokes prior installs (v1.js:3641). If two speakers must work the same list simultaneously, the conflict model has to be invented.
- Should the wordlist app share the EXISTING flextext-connectivity D1 + worker (one more command type, one more instance.type value, one more ALLOWED_ORIGINS entry) or get its own? The backend-first/additive rule (CLAUDE.md:633) makes sharing cheap but couples the two apps' deploy cadence; instance.type currently has a CHECK constraint IN ('editor','recorder','') that would need an additive migration.
- Where does Dekereke XML actually live in the Drive layout — as the per-text `<Storyname>/` folder analogue (one folder per elicitation session) or one file per wordlist? The `driveEnsureTextFolder` + appProperties docId tagging assumes one folder per unit of work.
- Is `paragraph-analysis/` (the PAT satellite, with its own paragraph-model.js/paragraph-ui.js and its own git-connected Worker) the closest precedent for how a wordlist app should be structured? It is the one satellite that carries its own engine modules and its own data model, and its deployment avoids the satellite deploy-order hazard entirely.
